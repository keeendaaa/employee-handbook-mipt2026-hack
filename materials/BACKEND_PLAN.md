# Бэкенд: исследование и предлагаемый план

Статус: **проект архитектуры, не реализация и не результат бенчмарка**. Подготовлено 12.11.2026 по [заданию](TASK.md), [критериям](CRITERIA.md), [проверке данных](DATA_PUBLICATION.md) и первичной документации ниже. Решения команды не являются требованиями организаторов.

## 1. Рекомендация

Сделать модульный Python-бэкенд с управляемым RAG-пайплайном и состоянием прохождения процедуры. Не давать LLM самостоятельно менять правила, выполнять действия за сотрудника или решать, какая редакция юридически приоритетнее без источников.

Предлагаемая основа:

| Компонент | Выбор для первого прототипа | Обоснование и ограничение |
|---|---|---|
| HTTP API и схемы | FastAPI + Pydantic | Структурированные ответы и OpenAPI; проверка схемы не доказывает истинность ответа. |
| Данные и поиск | PostgreSQL + pgvector | Одна БД для текстового и векторного поиска, источников, диалогов и планов. На начальном объеме — точный векторный поиск, без HNSW. |
| Лексический поиск | PostgreSQL full-text search, русская конфигурация + поиск реквизитов | Дополняет семантический поиск. Номера приказов, ФЛС и сокращения требуют отдельных тестов. Не называть стандартное ранжирование PostgreSQL алгоритмом BM25. |
| Embeddings | Кандидат `intfloat/multilingual-e5-small` локально | Есть русский язык, 384 измерения, MIT. Нужны префиксы `query:`/`passage:` и контроль длины по токенизатору, ориентир модели — 512 токенов. Это baseline, не доказанный победитель. |
| Генерация | Локальный llama-server; кандидат Qwen3-8B в GGUF | Есть локальное CPU/GPU-исполнение и schema-constrained JSON. Конкретную квантизацию, контекст и размер модели выбрать после измерений на доступном железе. |
| PDF | pypdf + Linux-совместимый рендеринг и Tesseract `rus+eng` | pypdf не распознает изображения. Вариант OCRmyPDF оценить на смешанных страницах; не брать его sidecar как полный текст документа. |
| DOCX | python-docx + адресная обработка XML нумерации | Читать параграфы и таблицы в исходном порядке, включая вложенные таблицы и необходимые колонтитулы. |
| XLSX | openpyxl | Читать структуру, формулы и отдельно доступные сохраненные значения; библиотека не пересчитывает формулы. |
| Хранилище оригиналов | Локальный volume | Не нужны S3/MinIO для 20 файлов. Исходники не включать в Git и Docker-образ. |

PostgreSQL выбран не потому, что 20 файлов требуют большой БД, а чтобы не поддерживать отдельно состояние приложения и поисковое хранилище. Если команда существенно быстрее работает с SQLite, допустим компактный вариант с локальным точным векторным поиском, но нужно отдельно проверить русский лексический поиск и конкурентные обновления.

Пока не нужны: Redis, Celery, отдельная векторная БД, Elasticsearch, LangChain/LangGraph, несколько LLM-агентов. Тяжелую индексацию запускать отдельной CLI-командой/одноразовым контейнером, не внутри HTTP-запроса и не как ненадежную долгую BackgroundTask.

## 2. Конфиденциальность — до выбора облачной модели

- Текущий статус набора: разрешение на публикацию и открытость не подтверждены. По умолчанию все извлечение, OCR, embeddings, reranking и генерация локальны.
- Отсутствие разрешения публиковать и отсутствие разрешения передавать API — разные вопросы. Ни один не считать автоматически решенным другим.
- Облачный провайдер — только после отдельного подтверждения допустимости передачи конкретных данных. Один флаг окружения сам по себе не легализует отправку.
- Контролировать весь payload: пользовательский вопрос, историю, цитаты, производные данные и телеметрию. Даже разрешенные документы не делают любой вопрос сотрудника открытым.
- Никакого автоматического fallback в облако при недоступности локальной модели. Ошибка должна быть видна.
- Логи по умолчанию содержат технические ID, длительность и коды ошибок, но не тексты документов, вопросов и ответов.
- Для локального MVP ограничить доступ локальной машиной. Публикация демо с реальными документами требует ограничения доступа; отсутствие регистрации не должно означать свободную раздачу источников.

## 3. Подготовка базы

Поток: `оригинал → проверка → извлечение/OCR → структурные блоки → версии и связи → фрагменты → индексы → отчет импорта`.

1. Проверить тип, размер, SHA-256, число страниц/размер распакованного Office-контейнера; задать таймауты и лимиты памяти. Не исполнять макросы, формулы и внешние ссылки.
2. PDF: извлекать текст постранично. На смешанных страницах сопоставлять текстовый слой с видимым содержимым; нельзя решать «OCR не нужен» только по ненулевой длине текста. Наш скрининг уже обнаружил такие страницы. Оригинал сохранять неизменным, OCR — отдельным производным артефактом.
3. Для Linux Docker использовать локальный переносимый OCR с установленным русским языком. Apple Vision из разового аудита не является воспроизводимым Linux-пайплайном.
4. DOCX: сохранять порядок заголовков, параграфов, таблиц, приложений; восстановление автоматической нумерации проверять отдельно. Номер страницы не выдумывать: Word переверстывает документ. Надежный резерв — путь заголовков, индекс блока и точный фрагмент.
5. XLSX: сохранять лист, диапазон, названия столбцов и строки, объединенные ячейки, формулу и кэшированное значение с пометкой происхождения. Пустой кэш не превращать в ноль. Не объявлять кэш проверенным расчетом.
6. Делить по смысловым пунктам. Для длинного пункта — дочерние фрагменты в лимите embedding-модели, с сохранением ссылки на родительский пункт. Для генерации добирать родителя, соседние условия и связанное приложение.
7. Не склеивать исходный текст и OCR вслепую: устранять дубли, сохранять способ извлечения и соответствие оригиналу. Конфликтующие числа/сроки помечать для проверки.
8. Повторный импорт того же хеша не создает дубли. Изменение файла создает новую версию; новая генерация индекса публикуется атомарно, старая сохраняется для уже выданных ссылок.
9. Ошибка одного документа видна в отчете. Частичный импорт не объявляется полной готовностью корпуса.

## 4. Модель данных

Минимальные сущности, без преждевременного построения универсального workflow-движка:

- `DocumentVersion`: стабильный ID документа, ID версии, имя, хеш, реквизиты, дата подписания, период действия, статус проверки применимости, статус конфиденциальности, результат импорта.
- `DocumentRelation`: приложение, изменение, отмена, замена; область изменения, основание-фрагмент, статус подтверждения. Не подразумевать полную замену при изменении одного пункта.
- `SourceBlock` / `Chunk`: исходный и нормализованный текст, заголовки, пункт, страница/диапазон/индекс блока, метод извлечения, родитель, версия embedding-модели.
- `Session` / `Message`: пользовательская цель, подтвержденные пользователем факты, нерешенные уточнения, сообщения, версия корпуса. Не считать прежний ответ модели нормативным источником.
- `PlanRevision` / `Step`: действие, условия применимости, зависимости, статус, ссылки на основания. Разделять нормативные требования и состояние пользователя.
- `StepEvent`: кто и когда отметил действие; статус `done_by_user` не равен фактическому одобрению или проверке документа организацией.

Факты сотрудника хранятся с происхождением «со слов пользователя». Извлеченные моделью нормативные утверждения всегда имеют основания. Даты и связи редакций могут дополняться проверенным реестром метаданных, но не отдельными зашитыми ответами на вопросы.

## 5. Поиск и ответ на каждом ходе

1. Прочитать цель и структурированные факты сессии. Если вопрос составной, выделить подзадачи, не изменяя намерение пользователя.
2. Выполнить лексический и семантический поиск; объединить результаты, например RRF. Начать с экспериментальных top-k, настраивать на проверочном наборе, не объявлять их универсальными.
3. Проверить реквизиты и применимость во времени; добрать связанные изменения, исходные пункты и приложения. Не отбрасывать старый документ целиком только из-за нового изменения.
4. Проверить покрытие каждой подзадачи. Высокая похожесть не означает наличие ответа. Низкое покрытие различать с повреждением индекса или недоступностью сервиса.
5. Если отсутствует факт пользователя, от которого зависит ветка процедуры, задать минимально необходимый вопрос и объяснить основание. Не запрашивать паспортные данные ради определения типа командировки.
6. Сформировать структурированный ответ: краткий вывод, шаги, уточнения, цитаты, непокрытые части и конфликты. Сначала строить доказательный ответ, затем представление для чата.
7. Проверить схему, существование ID источников, принадлежность нужным версиям, точность цитат и покрытие ключевых утверждений. URL, названия и локаторы подставляет сервер из реестра, не LLM.
8. Сопоставить смысл утверждений с основаниями. Это отдельная проверка: существующая цитата не гарантирует, что она подтверждает вывод. Дополнительный LLM-проверяющий тоже может ошибаться; нужны ручные эталоны.
9. При невалидной генерации допустима одна ограниченная попытка исправления с теми же основаниями; затем явная ошибка/сообщение об ограничении, но не выдуманный успешный ответ.

Статусы результата: `answered`, `needs_clarification`, `partial`, `not_found`, `conflict`. Технические ошибки — отдельные коды, не `not_found`. Не выдавать произвольный процент «уверенности» за вероятность правильности.

Schema-constrained JSON обеспечивает форму, не доказательность. Все цитаты привязаны к неизменяемой версии. Для OCR хранить распознанный фрагмент и возможность открыть оригинальную страницу; не называть его безошибочной транскрипцией.

## 6. Сопровождение сотрудника

Сценарий: цель → первичный план с условными/нерешенными шагами → отметки уже выполненного → уточнения, влияющие на оставшиеся действия → сопровождение → итог.

- Если без уточнения нельзя безопасно построить даже предварительный план, сначала уточнить. Не заставлять пользователя проходить анкету, не влияющую на действия.
- Модель предлагает план и изменения; сервер проверяет ссылки, зависимости и разрешенные изменения состояния.
- После нового факта пересчитывать только затронутую часть. Сохранять устойчивые ID шагов и историю версий. Существенно измененный выполненный шаг не наследует галочку автоматически.
- Бэкенд хранит прогресс между сообщениями и перезапусками; память процесса и текст истории чата недостаточны.
- Конкурентные изменения проверяются по версии плана; повтор запроса не должен дублировать сообщения и действия.
- Если корпус обновлен, обозначить изменение источников и необходимость перепроверки; не менять основания выполненных шагов молча.
- Выполнение чек-листа не означает фактическую подачу, оплату, согласование или соответствие всех пользовательских документов требованиям.

## 7. Предлагаемый API

Это проект контрактов, а не существующие endpoints:

| Метод и путь | Назначение |
|---|---|
| `POST /api/sessions` | Создать сессию; выдать непрозрачный токен доступа к ней. |
| `POST /api/sessions/{id}/messages` | Принять вопрос/уточнение; вернуть проверенный ответ и актуальную ревизию плана. |
| `GET /api/sessions/{id}` | Восстановить сообщения, факты и прогресс. |
| `PATCH /api/sessions/{id}/steps/{step_id}` | Изменить пользовательскую отметку с проверкой версии плана. |
| `GET /api/sources/{source_id}` | Получить название, фрагмент и локатор в оригинале; применять тот же контроль доступа. |
| `GET /health/live`, `GET /health/ready` | Различать живой процесс и готовность БД, модели и корпуса. |

Ответ сообщения содержит `result_type`, `summary`, `steps`, `clarifications`, `citations`, `missing_information`, `conflicts`, `plan_revision`, `corpus_revision`. Каждый шаг и существенное утверждение имеют ссылки на записи `citations`; ссылка только у всего ответа недостаточна.

Сначала обычный структурированный ответ. Для чат-ощущения можно позже передавать события поиска/проверки через SSE, но нормативный текст показывать после проверки, а не стримить неподтвержденные советы. Не публиковать раздачу всех документов как открытый endpoint.

## 8. Тренажер — после основного сценария

Отдельный необязательный режим, использующий те же версии источников, но другую сессию и отметку «учебный кейс». Факты синтетические, правила настоящие и подтвержденные. Проверять действия и объяснять ошибки цитатами. Для ситуации вне регламента правильным ответом может быть признание недостатка сведений. Учебные результаты не меняют рабочий прогресс и не являются аттестацией сотрудника.

Это полезная дополнительная возможность по О2.1, но не замена техническим требованиям. Не включать генератор тренажера в первую реализацию.

## 9. Развертывание

Предлагаемый Compose: `api` + `postgres` + `llm`; `ingest` — одноразовый запуск из образа приложения. Embeddings выполняются локально в приложении/индексаторе, OCR только в индексаторе.

- CPU-профиль должен быть документирован и проверен; GPU — отдельный профиль, не обязательная скрытая зависимость.
- На Mac для ускорения Metal может понадобиться отдельный host-процесс модели: не считать, что Linux Docker автоматически использует Apple GPU. Адрес модели задается конфигурацией; для проверки остается самостоятельный Linux CPU/GPU-путь.
- Оригиналы подключать read-only, результаты и БД — в отдельные volumes. `.dockerignore` должен исключать данные, логи и секреты из build context.
- Зафиксировать версии Python, зависимостей, контейнеров, моделей, токенизаторов, GGUF, chat template и схем. Сохранить проверяемые хеши; не использовать плавающие `latest` как воспроизводимую конфигурацию.
- Описать загрузку весов, требования к сети и диску и offline-запуск после подготовки. Веса без входящих пользовательских данных можно скачивать, но скрытых загрузок при первом запросе быть не должно.
- Нет модели/индекса — readiness неуспешна с понятной причиной. Публичный Git содержит код и синтетические примеры; реальные документы передаются проверяющим отдельно разрешенным способом.
- Настроить лимиты параллельной генерации, таймауты, длину запроса и контекста, отмену операций. Не обещать задержки и число пользователей до измерений.

## 10. Этапы и наблюдаемые результаты

1. **Эталоны и импорт.** Локально разметить проверочный набор, добиться учета 20/20 файлов, сохранения структуры и воспроизводимого Linux OCR. Прогнать поврежденный файл и повторную индексацию. Т1: 16 баллов.
2. **Поиск без генерации.** Возвращать документы и фрагменты; сравнить лексический, dense и hybrid. Проверить даты, изменения, составные вопросы. Т2: 20 баллов.
3. **Ответ с доказательствами.** Подключить модель, схемы, цитаты, частичные ответы, отказы и конфликты. Т3 + Т4: 36 баллов.
4. **Сопровождение.** Сохранение сессии, уточнения, чек-лист, пересчет и восстановление прогресса, ошибки. Т5: 8 баллов; сквозной сценарий для О1.
5. **Чистый запуск и документация.** Делать параллельно с этапа 1; финально проверить Docker/Compose, README и два use case без ручной правки кода. Т6: 20 баллов.
6. **Тренажер и защита.** Только после доказанного основного сценария; показывать пользу, ограничения и план внедрения.

Баллы выше — официальные максимумы соответствующих критериев, не обещание их получения.

## 11. Проверка качества до фиксации стека моделей

Предлагаемый первый набор — около 50 вопросов с покрытием всех 20 документов: прямые, перефразированные, составные, по редакциям, частично покрытые и отсутствующие. Конкретные эталоны составлять после нормативного чтения, а не по названиям файлов. Дополнительно — синтетические конфликтующие версии, prompt injection, поврежденные данные и сбои сервисов. Реальные фрагменты и эталоны хранить в игнорируемом локальном каталоге, например `data/review/eval/`.

Измерять отдельно: полноту нахождения правильных документов и фрагментов (Recall@k), приоритет первого нужного фрагмента, долю подтвержденных ключевых утверждений, полноту обязательных шагов, правильность отказов/частичных ответов, корректность редакций, задержку и пиковую память. Сравнить одинаковые вопросы на одинаковом корпусе; часть оставить контрольной, не настраивать систему на весь набор.

Стоп-факторы для MVP: вымышленные ссылки или требования, молча потерянные страницы, неотображенный сбой, несогласованная передача данных внешнему сервису, невоспроизводимый запуск. Нулевое число таких ошибок на тестах не гарантирует их отсутствия вообще. Пороговые показатели качества и задержек согласовать после baseline; официальных численных порогов в задании нет.

2. Сколько времени и людей есть на реализацию? Кто уже уверенно работает с Python/PostgreSQL?
3. Есть ли подтверждение допустимости внешних API и отдельное разрешение публикации?
4. Требует ли проверка расчетов по XLSX или только использования форм и положений?
5. Где будет демо и кто получит доступ к документам?

Без ответов можно реализовывать парсинг, локальный поиск, контракты и синтетические тесты. Покупку ресурсов, скачивание больших весов и выбор «окончательной лучшей модели» не выполнять автоматически.
